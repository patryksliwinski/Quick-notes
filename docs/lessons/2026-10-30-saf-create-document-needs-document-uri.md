# 2026-10-30 — SAF `createDocument` needs the tree's document URI, not the tree URI (issue #23)

- **Context:** Issue #23 — after switching the storage folder to a micro SD card, creating a note fell back to app-private storage with the "Selected folder is unavailable" snackbar; nothing landed in the selected folder. Follow-up to #16 (which fixed the crash but not the wrong-folder write).
- **Lesson:** `DocumentsContract.createDocument(resolver, parent, ...)` requires `parent` to be a **document URI** built from the tree URI via `DocumentsContract.buildDocumentUriUsingTree(treeUri, DocumentsContract.getTreeDocumentId(treeUri))`. Passing the raw `content://.../tree/<id>` URI works on some internal-storage paths but `ExternalStorageProvider` rejects it for removable volumes, so the create silently fails and the repository's `recover()` falls back to internal storage. Related gotcha found in the same function: `uri.lastPathSegment` of a SAF document URI is the encoded document ID, not the display name, so the atomic write's `renameDocument` must use `COLUMN_DISPLAY_NAME` (queried), not the path segment.
- **Rule now:** `SafNoteStore` derives `parentDocumentUri` once via `parentDocumentUriOf(treeUri)` and uses it for every `createDocument` call (create + temp file in `writeText`); `writeText` resolves the real display name through `COLUMN_DISPLAY_NAME` before renaming. Covered by `SafDocumentUriTest` (Robolectric); on-device SD-card behavior remains emulator-only per the Kover exclusions.
