# 2026-10-30 — A journaled-but-not-yet-written save is durable, not an error: `writeNote` returns `SaveOutcome`, no `StorageError` banner

- **Context:** Users reported "Could not save to the selected folder" (`NoteError.StorageError` snackbar) appearing when leaving the editor, while the note was in fact saved. Root cause: `NoteRepository.writeNote` always journals `(uri, content)` via `PendingSaveJournal.record()` *before* the store write, but on a store-write failure it set `StorageError` even though the journal entry keeps the content durable — `flushPendingSaves()` on next launch rewrites it. So a transient SAF write failure (which the durability design already treats as recovered, not lost) still produced a scary "couldn't save" message, and the error lingered in the shared `errorMessage` flow until the list screen consumed it.
- **Lesson:** Distinguish "the write failed" from "the content is not durable". The journal is the durability mechanism (write-ahead, `commit()`), so a failed store write with a live journal entry is `SaveOutcome.Journaled`, not an error; only a flush that still cannot write (`flushPendingSaves`, i.e. cold start after the failure persisted) surfaces `StorageError`. `writeNote` therefore returns `SaveOutcome.Written | Journaled` and never sets `errorMessage` on the journaled path.
- **Rule now:** `NoteRepository.writeNote` returns `SaveOutcome`; the catch block returns `Journaled` and leaves the journal entry intact without touching `errorMessage`; `flushPendingSaves` keeps setting `StorageError` only when the cold-start rewrite itself fails (and rethrows `CancellationException` so cancellation is not swallowed). Documented here; covered by `NoteRepositoryTest`.
