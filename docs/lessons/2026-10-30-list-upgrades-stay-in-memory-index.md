# 2026-10-30 — List upgrades (sort, day groups, count, filename search, confirm-delete) computed from the in-memory index only
- **Context:** issue #33 — sort-order toggle, day group headers, note count, filename search, and confirm-before-delete on the list screen, with hard constraints from #29/#30 that filtering/sorting/grouping must run over the in-memory `NoteMeta` list only (no `listNotes()`, no SAF queries, no per-keystroke file reads).
- **Lesson:** all five features are pure functions over `List<NoteMeta>` (`sortNotes`, `filterNotes`, `groupByDay` in `data/NoteListLogic.kt`) composed in the ViewModel's existing `combine()` flow, so per-keystroke work stays O(n) over a few hundred rows with cheap lowercase string ops. Two subtleties: (1) grouping by day must collect into a `LinkedHashMap` keyed by day, not emit a header on every day change — with title/filename sort the days interleave, and consecutive-change headers would fragment groups; (2) `today`/`yesterday` must be computed by comparing calendar day numbers, not `now - lastModified < 24h`, or a note from 23:59 yesterday lands under "Today". Sort order and confirm-delete are persisted in the same `quicknotes_prefs` SharedPreferences as the folder URI (`ListPrefs`), so selection survives process death without any disk scan of notes.
- **Rule now:** any list-screen transformation (sort/filter/group/count) is a pure, unit-tested function in `data/` over the in-memory `NoteMeta` index and recomputed in the ViewModel `combine()` flow; list UI prefs live in `ListPrefs` next to `FolderPrefs`; day grouping uses calendar-day comparison with a LinkedHashMap so headers never fragment under non-chronological sort orders.
