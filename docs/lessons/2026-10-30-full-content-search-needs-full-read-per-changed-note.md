# 2026-10-30 — Searching full note content costs one full read per *changed* note, not per note per refresh
- **Context:** issue #83 — list search only matched title/snippet (first 4 KiB head, 80-char snippet)/filename, so words deeper in a note were unfindable. Fix: `NoteMeta` carries the full `content`, matched via a precomputed lowercase field in `NoteSearch`.
- **Lesson:** the in-memory-index rule ("search filters `NoteMeta`, never disk per keystroke") forces full content to be *loaded* into the index. The trap to avoid is re-reading every note on every refresh; the correct shape is to read the full note once per `(uri, lastModified, size)` change and cache it next to the head fields, deriving title/snippet from the first 4 KiB of the same read — one `openInputStream` per changed file, zero extra reads for unchanged files, and `writeNote` updates the cached content in place. Widget head reads stay head-only (visible rows only).
- **Rule now:** `NoteRepository` caches full content in `contentCache` keyed by `HeadKey(uri, lastModified, size)` alongside `headCache`; search matches a precomputed `contentLower` in `NoteSearchEntry`; per-keystroke search remains pure in-memory `contains` over the index.
