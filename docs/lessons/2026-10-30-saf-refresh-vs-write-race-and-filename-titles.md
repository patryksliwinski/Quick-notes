# SAF refresh races the atomic write — and titles must not depend on content

- **Context:** Two long-standing SD-card complaints with the same underlying shape. (1) Open a note, go back, and the note vanishes from the list — sometimes reappearing on its own, sometimes only after reopening the app. (2) Rows sometimes show the file name as the title, sometimes the first line, depending on refresh timing.
- **Root cause:** `SafNoteStore.writeText` publishes changes via a rename swap (`a.md` → `.a.md.bak`, tmp → `a.md`). `MainActivity.onResume` and `NotesListScreen`'s `LaunchedEffect` both trigger `repository.refresh()` — exactly while the editor's `onDispose { saveNow() }` is mid-swap. `listNotes()` runs between the two `renameDocument` calls and sees *neither* file, so the row disappears. Because the repository then re-inserts the note from in-memory state on the write's completion (or a later refresh finds it), it "comes back". The title flip had the same shape: the list first publishes a placeholder head (`deriveTitle(name, "")` → file name), then replaces it with a content-derived title once the (slow, on SD) `readNote` finishes — every refresh raced this, so the same row flipped between file name and first line.
- **Lesson:** A listing is a *snapshot*, not a source of truth for liveness. Two fixes, both needed: (a) serialize listing vs mutation inside the store — a per-tree-URI mutex (`ConcurrentHashMap<String, Mutex>`, shared across store instances because the repository re-resolves a fresh store each refresh) around `listNotes`/`writeNote`/`createNoteWithContent`/`restoreNote`/`deleteNote`, so the listing never observes the mid-swap window; (b) belt-and-braces at the repository: a refresh retains in-memory entries whose URI still has a journal entry pending — a note with a not-yet-durable write is never dropped just because one listing missed it. And the display rule that removes the flip entirely: the **title is always the file name** — a title that depends on content depends on I/O timing, and on removable storage that timing is exactly what you cannot rely on. Content still powers the snippet and search; the title stays a pure function of the name.
- **Also:** `NotesViewModel.refresh()` used to *drop* refresh requests that arrived while one was in flight — the onResume refresh swallowed the post-write refresh. Queue one trailing refresh instead, so the list always reflects the just-completed write.
