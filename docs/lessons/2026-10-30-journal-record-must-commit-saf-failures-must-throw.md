# 2026-10-30 — Durability path must be synchronous; SAF failures must throw, never return "" (issue #58)

- **Context:** Issue #58 reported notes empty after reopening the app, especially on SD-card folders. Three root causes: (1) `PendingSaveJournal.record` used `SharedPreferences.Editor.apply()`, which is asynchronous — a process kill inside the 400 ms debounce could happen before the journal entry hit disk, so `flushPendingSaves()` found nothing; (2) `SafNoteStore.readNote`/`listNotes`/`readHead` returned `""`/empty list when `openInputStream`/`query` returned null (volume unmounted, permission hiccup), and `EditorViewModel.open` loaded that `""` into the editor, after which the next autosave overwrote the real file with empty content; (3) `NoteRepository.deleteNote` deleted even when the pre-delete read failed, so undo restored an empty note.
- **Lesson:** On the durability path, "asynchronous" is not "eventually" — `apply()` gives no crash guarantee, so the write-ahead journal must use `commit()` (only `clear` may stay async). And a storage layer must never convert an unavailable volume into empty content: SAF null results (null cursor, null input stream) are errors and must throw, because `""` is indistinguishable from a genuinely empty note at the call site and gets autosaved over the real file. Belt-and-braces at the repository layer: `readNote` returns a `Result` and treats an empty read of a note the index reports as non-empty (`size > 0`) as unreadable; the editor blocks autosave/save-on-leave while the load failed; delete reads before deleting and aborts on failure so undo keeps real content.
- **Rule now:** `PendingSaveJournal.record` uses `commit()`; `SafNoteStore` throws `IOException` on null query/input stream; `NoteRepository.readNote` returns `Result<String>` with a `size > 0` empty-read guard; `EditorViewModel` never autosaves after a failed load; `deleteNote` aborts when the pre-delete read fails. Documented in `docs/ARCHITECTURE.md` ("Durability on the quick-leave path").
