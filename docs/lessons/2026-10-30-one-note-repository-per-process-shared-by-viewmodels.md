# 2026-10-30 — One NoteRepository per process, shared by all ViewModels (issue #57)

- **Context:** Bug report (issue #57): `NotesViewModel` and `EditorViewModel` each constructed their own `NoteRepository`, so each had its own `_notes` StateFlow and head cache. Editor-side mutations (duplicate, autosave) were written to disk but never reached the list's flow until the next `onResume` refresh — duplicate notes were missing from the list and the title/sort position looked stale until the app was reopened.
- **Lesson:** A repository that owns a mutable in-memory index is only a "single source of truth" if there is exactly one instance. ViewModels that both observe and mutate the same domain state must receive the same repository, not construct their own — do this with an application-scoped holder (`NoteRepositoryHolder.get(application)`) as the default constructor argument, keeping an injectable constructor parameter for tests. Tests should wire both ViewModels against one instance the way the UI does; otherwise the split wiring is never exercised.
- **Rule now:** `NotesViewModel` and `EditorViewModel` default to `NoteRepositoryHolder.get(application)` (process-wide singleton, double-checked locking) and accept an optional `NoteRepository` constructor parameter for tests. Documented in `docs/ARCHITECTURE.md` data-flow step 0; covered by `SharedNoteRepositoryTest`.
